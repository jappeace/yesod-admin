#+TITLE: Django Admin vs Haskell Frameworks: Investigation Report
#+AUTHOR: Claude Opus 4.6
#+DATE: 2026-05-07

* Executive Summary

Django's admin is the gold standard for auto-generated CRUD interfaces: one line
of code (~admin.site.register(Model)~) gives you a fully functional back-office
UI. The Haskell ecosystem has *nothing comparable*. IHP comes closest with
schema-driven code generation, but requires explicit scaffolding per entity.
Yesod has no usable admin solution -- every attempt was abandoned by 2016. The
gap represents both a missing feature and an architectural challenge rooted in
how Haskell's type system handles runtime introspection.

* How Django Does Admin Pages

** Architecture

Django's admin is built on three core components:

- *AdminSite* -- a singleton that owns a ~_registry~ mapping Model classes to
  ModelAdmin instances. Handles URL routing for the entire admin, manages
  site-wide settings, and can be subclassed for separate admin interfaces.
- *ModelAdmin* -- the intermediary between a model and the admin UI. Controls
  list views, form generation, permissions, and actions. Initialized once at
  startup (not per-request).
- *ChangeList* -- renders the list/overview page. Manages the pipeline:
  ~get_queryset()~ \to filters \to ordering \to search.

*Autodiscovery*: when ~django.contrib.admin~ is in ~INSTALLED_APPS~, Django
scans every app for an ~admin.py~ module, imports it, and all
~admin.site.register()~ calls populate the registry.

*Required infrastructure*: auth, contenttypes, messages, sessions -- the admin
depends on Django's permission system and session management.

** Auto-Generation from Models

The key mechanism is *runtime model introspection* via Python's ~_meta~
attribute. Every Django model exposes:

- All field definitions (name, type, constraints)
- Relationships (ForeignKey, ManyToMany)
- Verbose names, help text, choices
- Validation rules (blank, null, max_length, etc.)

Each model field maps to a form widget automatically:

| Model Field     | Widget          |
|-----------------+-----------------|
| CharField       | TextInput       |
| TextField       | Textarea        |
| BooleanField    | CheckboxInput   |
| DateTimeField   | DateTimeInput   |
| ForeignKey      | Select dropdown |
| ManyToManyField | SelectMultiple  |
| Field w/choices | Select dropdown |

Form fields inherit model metadata: ~required~ from ~blank~, ~label~ from
~verbose_name~, ~help_text~, ~max_length~. This means model changes
automatically propagate to the admin UI with zero code changes.

** Minimal Registration

#+begin_src python
from django.contrib import admin
from myapp.models import Article

admin.site.register(Article)
#+end_src

This single line produces: list page with all articles, add/edit/delete forms
with correct widgets, change history tracking, and pagination.

** Key Features

- *list_display* -- controls which columns appear in the list view. Supports
  model fields, related fields via =__= notation, callable methods with
  =@admin.display= decorator.
- *search_fields* -- adds a search box. Supports prefix modifiers: =^=
  (startswith), ~=~ (exact), =@= (full-text).
- *list_filter* -- adds a filter sidebar. Custom filters via ~SimpleListFilter~.
- *Inline editing* -- edit related objects (e.g. chapters of a book) on the
  same page as the parent, using ~TabularInline~ or ~StackedInline~.
- *list_editable* -- edit fields directly in the list view without opening
  the detail page.
- *Actions* -- bulk operations on selected objects (publish, export CSV, etc.).
- *Permissions* -- four levels per model (view, add, change, delete) with
  object-level granularity. Integrated with Django's auth framework.

** Customization Depth

Django's admin has extraordinary extension points:

- *Fieldsets* -- group fields into collapsible sections
- *Dynamic per-request behavior* -- every attribute has a ~get_*()~ method
  that receives the request (e.g. ~get_readonly_fields~, ~get_queryset~,
  ~get_list_display~)
- *Custom views* -- inject custom URLs via ~get_urls()~
- *Template overrides* -- per-model or global, using block inheritance
- *Multiple AdminSites* -- entirely separate admin interfaces with different
  models, permissions, and branding
- *Save/delete hooks* -- ~save_model()~, ~save_related()~, ~delete_model()~
- *Foreign key filtering* -- ~formfield_for_foreignkey()~ to restrict dropdowns

** Strengths

- *Zero-to-CRUD in one line* -- unmatched by any framework in any language
- *Deep model introspection* -- model changes propagate automatically
- *30+ attributes, ~50 overridable methods* on ModelAdmin
- *Battle-tested maturity* -- core component since 2005, used by thousands of
  organizations for two decades
- *Inline editing* of related objects (non-trivial to build by hand)

** Weaknesses

- *Not for end users* -- Django's own docs say it is for "trusted internal
  users," not public-facing
- *Model-centric, not process-centric* -- poor fit for multi-step workflows
  or wizards
- *ForeignKey performance trap* -- default Select widget loads ALL related
  objects (catastrophic for large tables)
- *Tightly coupled to Django ORM* -- cannot work with external APIs or
  non-Django data sources
- *Limited UI/UX flexibility* -- server-rendered forms, adding rich
  client-side interactivity requires escaping the paradigm
- *No built-in 2FA or brute-force protection*
- *Complexity cliff* -- simple customizations are trivial, but significantly
  non-standard behavior requires overriding many interacting methods

* Haskell Framework Comparison

** Yesod

*Status*: Actively maintained core (yesod 1.6.x, persistent 2.14+, 2025).
Admin/CRUD packages: *all dead*.

*No built-in admin*. Yesod's philosophy is "type-safe building blocks" rather
than "batteries-included admin." Developers manually compose Persistent +
yesod-form + isAuthorized.

*** Typical CRUD Pattern

Every entity requires this boilerplate:

#+begin_src haskell
-- Model (via Persistent TH)
share [mkPersist sqlSettings, mkMigrate "migrateAll"] [persistLowerCase|
Tutorial
    title Text
    content Text
    deriving Show
|]

-- Routes
-- /tutorials              TutorialsR  GET POST
-- /tutorials/#TutorialId  TutorialR   GET POST DELETE

-- Form
tutorialForm :: Maybe Tutorial -> AForm Handler Tutorial
tutorialForm mTutorial =
  Tutorial
    <$> areq textField "Title"   (tutorialTitle   <$> mTutorial)
    <*> areq textareaField "Content" (tutorialContent <$> mTutorial)

-- Handler (one of several required)
postTutorialsR :: Handler Html
postTutorialsR = do
    ((result, _), _) <- runFormPost $
        renderBootstrap3 BootstrapBasicForm (tutorialForm Nothing)
    case result of
        FormSuccess tutorial -> do
            _ <- runDB $ insert tutorial
            redirect TutorialsR
        _ -> redirect TutorialsR
#+end_src

*** Type Safety Trade-offs

*Type safety helps*: route safety (broken links are compile errors), form
safety (~FormSuccess~ gives a validated value), authorization pattern-matches on
route constructors.

*Type safety hinders*: no generic reflection over entities (the fundamental
reason auto-admin is hard), boilerplate per entity, subsite complexity far
exceeds Django's ~admin.site.register()~.

A *GSoC 2025 proposal* existed for auto-generated admin pages in Yesod -- it
has not materialized into working code.

** IHP (Integrated Haskell Platform)

*Status*: Actively maintained (v1.5.0, March 2026). 5,283 GitHub stars. Backed
by digitally induced (commercial company).

*Closest to Django in the Haskell world*, but with a fundamental difference:
IHP *scaffolds* CRUD (generates source files you own) rather than
*auto-generating* it at runtime.

*** Schema-First Approach

The inverse of Django:

| Aspect          | Django                         | IHP                                  |
|-----------------+--------------------------------+--------------------------------------|
| Source of truth | Python model classes           | PostgreSQL DDL (~Schema.sql~)        |
| Type generation | Manual Python class definition | Automatic from SQL at compile time   |
| Migrations      | ~makemigrations~ / ~migrate~   | Direct schema editing + "Migrate DB" |
| DB features     | Abstracted through ORM         | Full PostgreSQL access               |
| Type safety     | Runtime only                   | Compile-time guaranteed              |

*** Code Generation

From the web-based dev IDE (port 8001), you name a controller and IHP generates:

- Controller data type with all CRUD actions (7 constructors)
- Route registration
- Controller implementation with handlers for index/show/new/create/edit/update/delete
- Four view files (Index, Show, New, Edit)

The generator is *schema-aware*: it reads ~Schema.sql~, infers column types,
generates appropriate form field helpers, and suggests validation
(e.g. ~nonEmpty~ for non-null text, ~isEmail~ for email columns).

*** Admin Pattern

IHP supports multiple applications within a project. You run
~new-application admin~ to create a separate =Admin/= directory, then scaffold
CRUD controllers within it. Not automatic, but fast (minutes per entity).

*** HSX Templates

Quasi-quoted HTML (~[hsx| ... |]~) that compiles to BlazeHtml. Compile-time
validation of tags, attributes, and type correctness. XSS escaping by default.

*** Advantages and Disadvantages vs Django

*Key advantage*: generated code is fully visible, editable, and type-checked.
Renaming a column in ~Schema.sql~ causes compiler errors everywhere the old name
is referenced.

*Key disadvantage*: you must explicitly scaffold each entity. No "register and
go" pattern.

** Other Haskell Frameworks and Libraries

- *Servant* -- type-level API DSL. No admin or CRUD generation.
  ~servant-util-beam-pg~ provides auto filter/sort/paginate but no UI.
- *Scotty* -- minimal Sinatra-like. Zero admin capabilities.
- *Beam* -- type-safe database library. No UI generation.
- *Hyperbole* -- server-side interactive HTML (inspired by HTMX/LiveView).
  Actively maintained (v0.6.1, April 2026). Promising but no auto-generation.
- *digestive-functors* / *reform* -- form libraries, actively maintained, but
  require manually composing every form field. No auto-derivation from types.
- *generics-sop* -- provides type-level metadata (constructor names, field names)
  that /could/ power auto-generated forms. Nobody has built this.
- *regular-web* (2010) -- the closest historical attempt at generic form
  generation from Haskell types. Dead for 15+ years.

* The Fundamental Gap

** Why Django Can Do This and Haskell Can't (Easily)

Django's admin works because Python enables *trivial runtime introspection*:

#+begin_src python
for field in model._meta.fields:
    print(field.name, field.__class__.__name__, field.choices)
#+end_src

In Haskell, the equivalent requires either:

1. *Template Haskell* -- generates code at compile time from model definitions
   (Persistent does this for DB ops, nobody has done it comprehensively for admin UIs)
2. *GHC Generics / generics-sop* -- provides type-level metadata that can be
   walked generically. The infrastructure exists but no one has wired it to
   produce web forms + CRUD handlers
3. *Typeable / Data* -- "Scrap Your Boilerplate" style. The abandoned
   ~regular-web~ (2010) used this approach

The technical barrier is not insurmountable -- the pieces exist. The social
barrier is that the Haskell web ecosystem is small, and the few developers who
work in it tend to value explicit control over auto-generation.

** Feasibility: TH-Generated Admin from Persistent EntityDef

Rather than runtime introspection (Django) or external code generation (IHP), a
third approach exists: *compile-time generation via Template Haskell*, using the
same entity definitions that ~mkPersist~ already consumes. This would give Yesod
the same "one line to CRUD" developer experience as Django, but with compile-time
type safety.

*** The ~share~ Combinator Makes This Idiomatic

Persistent's ~share~ applies multiple TH generators to the same
~[UnboundEntityDef]~. A custom ~mkAdmin~ plugs in alongside ~mkPersist~:

#+begin_src haskell
share
    [ mkPersist sqlSettings
    , mkMigrate "migrateAll"
    , mkAdmin                  -- generates routes, handlers, forms
    ]
    [persistLowerCase|
        User
            name Text
            email Text
            age Int Maybe
        Post
            title Text
            authorId UserId
    |]
#+end_src

This is the Django equivalent of ~admin.site.register(User, Post)~ -- except it
runs at compile time and produces type-checked Haskell code.

*** Available Metadata

The ~UnboundEntityDef~ received by the TH splice contains everything needed:

*EntityDef level*:
- ~entityHaskell~ -- Haskell type name (e.g. "User")
- ~entityDB~ -- database table name (e.g. "user")
- ~entityId~ -- primary key definition (surrogate or composite)
- ~entityUniques~ -- uniqueness constraints
- ~entityForeigns~ -- foreign key relationships

*FieldDef level* (per field):
- ~fieldHaskell~ -- field name (e.g. "email")
- ~fieldType~ -- parsed type (~FTTypeCon Nothing "Text"~, ~FTTypeCon Nothing "Int"~, etc.)
- ~fieldAttrs~ -- attributes including ~FieldAttrMaybe~, ~FieldAttrDefault~, ~FieldAttrMaxlen~
- ~fieldReference~ -- ~ForeignRef entityName~ for FK fields

All of these types have ~Lift~ instances, so they are fully available at compile
time.

*** Field Type to Form Widget Mapping

The TH splice pattern-matches on ~FieldType~ to choose the appropriate Yesod
form field:

#+begin_src haskell
fieldTypeToFormField :: FieldType -> Q Exp
fieldTypeToFormField = \case
    FTTypeCon Nothing "Text"      -> [| textField |]
    FTTypeCon Nothing "Int"       -> [| intField |]
    FTTypeCon Nothing "Int64"     -> [| intField |]
    FTTypeCon Nothing "Double"    -> [| doubleField |]
    FTTypeCon Nothing "Bool"      -> [| checkBoxField |]
    FTTypeCon Nothing "Day"       -> [| dayField |]
    FTTypeCon Nothing "TimeOfDay" -> [| timeField |]
    FTTypeCon Nothing "UTCTime"   -> [| datetimeLocalField |]
    FTTypeCon Nothing "Textarea"  -> [| textareaField |]
    FTTypeCon Nothing name
        | "Id" `T.isSuffixOf` name -> [| selectField optionsFromEntity |]
    _                              -> [| textField |]  -- fallback
#+end_src

Nullable fields (detected via ~FieldAttrMaybe~ in ~fieldAttrs~) use ~aopt~
(optional) instead of ~areq~ (required).

*** What the Generated Code Would Look Like

For each entity, ~mkAdmin~ would generate:

*1. Route types* (or a subsite):

#+begin_src haskell
-- Generated for "User" entity
data AdminUserR
    = AdminUserListR           -- GET: list all users
    | AdminUserCreateR         -- GET: new form, POST: create
    | AdminUserEditR UserId    -- GET: edit form, POST: update
    | AdminUserDeleteR UserId  -- POST: delete
#+end_src

*2. List handler* with pagination:

#+begin_src haskell
getAdminUserListR :: Handler Html
getAdminUserListR = do
    users <- runDB $ selectList [] [Asc UserName]
    defaultLayout $(adminListWidget ''User)
#+end_src

*3. Form* (generated from field metadata):

#+begin_src haskell
adminUserForm :: Maybe User -> AForm Handler User
adminUserForm mUser = User
    <$> areq textField "Name"  (userName  <$> mUser)
    <*> areq textField "Email" (userEmail <$> mUser)
    <*> aopt intField  "Age"   (userAge   <$> mUser)  -- Maybe -> aopt
#+end_src

*4. Create/Edit/Delete handlers*:

#+begin_src haskell
postAdminUserCreateR :: Handler Html
postAdminUserCreateR = do
    ((result, widget), enctype) <- runFormPost $
        renderBootstrap3 BootstrapBasicForm (adminUserForm Nothing)
    case result of
        FormSuccess user -> do
            _ <- runDB $ insert user
            redirect AdminUserListR
        _ -> defaultLayout $(adminFormWidget widget enctype)
#+end_src

*** The Subtlety: ~UnboundEntityDef~ vs Resolved ~EntityDef~

The ~UnboundEntityDef~ received via ~share~ has slightly incomplete resolution --
~fieldSqlType~ and some ~fieldReference~ values are filled in later by
~mkPersist~'s internal processing. Two strategies:

- *Strategy A* (simpler): Pattern-match on ~FieldType~ text names (e.g.
  ~FTTypeCon Nothing "Text"~). This is fully available in ~UnboundEntityDef~ and
  sufficient for widget mapping. FK fields are detectable by the "Id" suffix
  convention.

- *Strategy B* (more robust): Use ~mkEntityDefList~ to get fully resolved
  ~[EntityDef]~ in a separate TH splice group, then feed those into the admin
  generator:

#+begin_src haskell
share [mkPersist sqlSettings, mkEntityDefList "entityDefs"] [persistLowerCase| ... |]

$(pure [])  -- splice group barrier

mkAdmin entityDefs  -- receives fully resolved EntityDefs
#+end_src

Strategy A is simpler and keeps everything in one splice. Strategy B gives
access to ~fieldSqlType~ and fully resolved ~fieldReference~ as a fallback.

*** Comparison with Django's Approach

| Aspect               | Django (runtime)               | Proposed TH approach             |
|----------------------+--------------------------------+----------------------------------|
| When it runs         | Every request (introspection)  | Once at compile time             |
| Type safety          | Runtime errors                 | Compile-time errors              |
| Model change impact  | Automatic (next request)       | Automatic (next compile)         |
| Broken field refs    | Runtime ~AttributeError~       | Compile error                    |
| Widget mapping       | ~_meta~ field class dispatch   | ~FieldType~ pattern matching     |
| FK dropdowns         | ~ModelChoiceField~ (all rows)  | ~selectField~ (configurable)     |
| Customization        | ~ModelAdmin~ class overrides   | Typeclass instances (TBD)        |
| Code visibility      | Hidden behind framework        | Generated Haskell, inspectable   |
| Developer experience | ~admin.site.register(Model)~   | ~mkAdmin~ in ~share~ block       |

*** Open Design Questions

1. *Routing*: Generate a Yesod subsite? Or standalone routes with a prefix? A
   subsite is more composable but adds complexity.

2. *Customization*: Django uses ~ModelAdmin~ class attributes. The Haskell
   equivalent could be a typeclass:

#+begin_src haskell
class AdminEntity a where
    adminListFields   :: Proxy a -> [Text]      -- which fields to show in list
    adminSearchFields :: Proxy a -> [Text]      -- which fields are searchable
    adminReadonly     :: Proxy a -> [Text]      -- read-only fields
    -- defaults via DefaultSignatures from EntityDef metadata
#+end_src

3. *Templates*: Generate Hamlet widgets? Or return raw HTML via blaze? Hamlet
   integrates better with Yesod but adds a TH-within-TH complexity.

4. *Permissions*: Hook into Yesod's ~isAuthorized~ or generate its own auth
   checks?

5. *Foreign key widgets*: Eager-load all related entities (Django's default,
   dangerous for large tables) or use AJAX autocomplete?

*** Verdict

This is *feasible and novel*. No existing Haskell library takes this approach.
The metadata is available, the TH machinery is proven (Persistent already uses
it extensively), and the ~share~ combinator provides the idiomatic integration
point. The result would be Django-like DX with compile-time safety -- the best
of both worlds.

The main engineering challenge is not "can it be done" but "how much of Django's
20 years of refinement can be replicated in a reasonable scope."

* Recommendations

** For the RAD Investigation Project

1. *Django's admin is the benchmark* -- any Haskell solution should be measured
   against the "one line to CRUD" developer experience.

2. *A TH-based approach using Persistent's ~EntityDef~ is the recommended path*.
   The ~share~ combinator provides the idiomatic integration point. A custom
   ~mkAdmin~ splice can generate routes, handlers, and forms from the same
   entity definitions that ~mkPersist~ uses -- giving Django-like DX with
   compile-time type safety. This approach is novel: no existing library does it.

3. *Start with Strategy A* (pattern-matching on ~FieldType~ text names in
   ~UnboundEntityDef~). This is simpler than waiting for fully resolved
   ~EntityDef~ and covers the common cases (Text, Int, Bool, Day, FK via "Id"
   suffix).

4. *Customization via a typeclass with ~DefaultSignatures~* is the Haskell
   analogue to Django's ~ModelAdmin~. Users get sensible defaults from entity
   metadata but can override per-entity.

5. *Don't replicate Django's weaknesses* -- a Haskell admin should:
   - Handle ForeignKey fields efficiently from the start (no "load all rows" default)
   - Support process-centric workflows, not just table-centric CRUD
   - Provide compile-time guarantees that Django's runtime approach cannot

6. *IHP's approach* (schema-driven external code generation) remains a viable
   alternative if TH complexity becomes prohibitive, but it sacrifices the
   "one splice to CRUD" developer experience.
